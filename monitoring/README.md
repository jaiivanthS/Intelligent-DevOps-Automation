# Monitoring (Prometheus · Grafana · Loki · Alertmanager)

Runs on the **app host**, next to `demo-app`, on the shared `devops-net` Docker network.

```
demo-app ──/metrics──▶ Prometheus ──rules──▶ Alertmanager ──webhook──▶ platform incident collector (step 6)
   │ stdout (JSON)         ▲  ▲ ▲
   ▼                       │  │ └── node-exporter (both hosts), cAdvisor (containers), Jenkins /prometheus/
Promtail ──▶ Loki ◀── Grafana (dashboards: metrics + logs side by side)
```

| Component | Port | Purpose |
|---|---|---|
| Prometheus v3.1 | 9090 (admin IPs) | Scraping, recording rules, alert rules, 15-day retention |
| Alertmanager v0.28 | 127.0.0.1:9093 | Groups alerts and sends them to `platform-api:8000/api/alerts/alertmanager` |
| Grafana 11.4 | 3000 (admin IPs) | Data sources and dashboards are provisioned from code; no anonymous access |
| Loki 3.3 | 127.0.0.1:3100 | Log store (filesystem, 7-day retention) |
| Promtail 3.3 | – | Discovers Docker containers and parses demo-app's JSON logs |
| cAdvisor 0.49 | – | Per-container CPU and memory |
| loadgen | – | Sends about 2 req/s of realistic traffic, so rates and alerts have data |

## Start

On the app host, after the first deployment (or on its own, since it creates `devops-net`):

```bash
cd Intelligent-DevOps-Automation/monitoring
./setup.sh                 # creates .env with a random Grafana password, starts the stack
grep GRAFANA_ADMIN_PASSWORD .env
./setup.sh --reload        # after editing prometheus.yml or rules
```

## Alerts

All alerts carry `severity`, `category` and `service` labels. The incident
collector and the RCA engine rely on these labels.

| Alert | Category | Fires when | Typical fault |
|---|---|---|---|
| `DemoAppDown` | availability | scrape fails for 1 minute | crash, bad deploy |
| `HighErrorRate` | errors | 5xx ratio > 5% for 2 minutes | `error_rate` |
| `HighLatencyP95` | latency | p95 > 500 ms for 2 minutes | `latency_ms`, `cpu_burn_ms` |
| `DependencyDown` | dependency | `dependency_up == 0` for 1 minute | `dependency_failure` |
| `HighMemoryUsage` / `MemoryGrowing` | saturation | RSS > 400 MiB / sustained growth | `memory_leak_mb` |
| `HighCpuUsage` | saturation | > 0.8 core for 2 minutes | `cpu_burn_ms` |
| `TooManyInFlightRequests` | saturation | > 20 concurrent requests | latency or overload |
| `HostHighCpu` / `HostHighMemory` / `HostDiskAlmostFull` | saturation | host resources | – |
| `JenkinsDown`, `MonitoringTargetDown` | ci / availability | component unreachable for 5 minutes | – |
| `ChaosInjectionActive` | experiment | a fault is being injected | **ground truth only**, never an RCA input |

Inhibition rules: `DemoAppDown` silences the other alerts for that service, and
`DependencyDown` silences the `HighErrorRate` alert it causes.

## Dashboards

Dashboards are generated by `grafana/build_dashboards.py`. Edit that script, then run it again:

* **demo-app: Service Overview** has RED stats (request rate, error ratio, p95 latency),
  dependency status, requests and errors by route, latency percentiles, memory, CPU,
  in-flight requests, active failure injection, and error and request logs from Loki.
* **Infrastructure: Hosts & Containers** shows host CPU, memory, disk and network,
  container CPU and memory, scrape-target health and firing alerts.

## Useful LogQL

```logql
{service="demo-app", level="ERROR"}
{service="demo-app", status_class="5xx"} | json | line_format "{{.route}} {{.status}} {{.duration_ms}}ms"
sum by (route) (count_over_time({service="demo-app", event="http_request"} | json | duration_ms > 500 [5m]))
```
